API FastAPI : /health, /predict, schémas Pydantic

Ce qui a été fait
L’API expose un endpoint de supervision /health et un endpoint métier /predict. Les entrées et sorties sont typées et validées avec des schémas Pydantic.
Pourquoi c’est utile
FastAPI permet d’exposer le modèle de manière testable et documentée. /health sert au diagnostic rapide, /predict matérialise le service métier, et Pydantic protège l’API contre les payloads invalides.
Où on en est maintenant
L’API répond localement, charge le modèle, retourne une probabilité, une décision binaire et un seuil, et remonte aussi l’état de la base dans /health.
Preuve dans le dépôt
openclassrooms_projet5/api/main.py · openclassrooms_projet5/api/schemas.py · README.md

Persistance PostgreSQL optionnelle

Ce qui a été fait
Une couche de persistance synchrone a été ajoutée avec SQLAlchemy pour enregistrer chaque prédiction réussie dans PostgreSQL quand DATABASE_URL est renseignée.
Pourquoi c’est utile
La base apporte de la traçabilité sans transformer l’API en dépendance fragile : la prédiction continue à répondre même si la journalisation échoue, ce qui est un choix pragmatique pour une première version.
Où on en est maintenant
La journalisation est implémentée et validée avec une base active. Sans base, le comportement reste fonctionnel et l’API signale simplement que la journalisation est désactivée.
Preuve dans le dépôt
openclassrooms_projet5/api/main.py · openclassrooms_projet5/db/models.py · openclassrooms_projet5/db/service.py

Pourquoi ces choix

FastAPI

Le but du projet n’est pas seulement d’avoir un modèle, mais un service exploitable. FastAPI donne une API claire, testable, documentée automatiquement et adaptée à une démonstration mentor ou soutenance.

/health et /predict

/predict matérialise la valeur métier. /health sert à distinguer rapidement un problème de modèle, de configuration ou de base de données, ce qui est important pour l’exploitation.

Pydantic

Valider les entrées et les sorties évite d’envoyer au modèle des données incohérentes et clarifie le contrat JSON de l’API.

PostgreSQL optionnel

La traçabilité est utile pour auditer les prédictions, mais je n’ai pas voulu rendre l’API inutilisable si la base manque. Le mode optionnel est un bon compromis pour une v1.

SQLAlchemy + Alembic

SQLAlchemy apporte une couche standard côté application. Alembic versionne le schéma et rend l’évolution de la base traçable et reproductible.

compose.yaml et .env.example

Ces fichiers rendent le projet relançable sur une machine propre, avec une configuration explicite et un PostgreSQL local rapide à démarrer.

CI GitHub Actions

L’objectif est d’éviter une qualité “ça marche chez moi”. Le pipeline vérifie automatiquement les tests, la qualité de code et le scénario avec base de données.

Artefact modèle chiffré

Le modèle du projet 4 doit être disponible pour la CI sans exposer un binaire sensible en clair dans le dépôt. Le chiffrement garde un niveau de sécurité tout en permettant la reproductibilité.

Tests d’intégration

Ils démontrent que la journalisation fonctionne réellement avec la base et la migration, et pas seulement sur le papier ou via des mocks.

Depuis la dernière session, j’ai structuré le projet pour qu’il ne soit plus seulement une idée d’API autour du modèle du projet 4, mais un vrai socle technique présentable et testable. L’objectif du projet reste de transformer le modèle d’attrition en service exploitable. Pour ça, j’ai conservé une architecture simple mais propre, avec FastAPI pour exposer le modèle, Pydantic pour valider les entrées et sorties, et une documentation de démarrage pour pouvoir relancer le projet rapidement. Concrètement, j’ai une API qui expose deux routes principales. La première est /health, qui me permet de vérifier que l’application répond, que le modèle est bien chargeable, et maintenant aussi que la base de données est disponible ou non. La seconde est /predict, qui prend les données d’un employé, exécute l’inférence et retourne la probabilité d’attrition, la prédiction binaire et le seuil utilisé. J’ai aussi ajouté une brique PostgreSQL optionnelle. Le but n’était pas de rendre la base obligatoire tout de suite, mais d’apporter de la traçabilité. Maintenant, quand la variable DATABASE_URL est configurée, chaque prédiction réussie peut être journalisée en base. J’ai volontairement gardé un comportement best effort : si la base n’est pas disponible, l’API continue à répondre. Pour moi, c’est un choix pragmatique pour une première version, parce que je privilégie d’abord la continuité du service, tout en préparant la traçabilité. Pour rendre cette partie base de données propre, j’ai ajouté SQLAlchemy côté application et Alembic pour les migrations. J’ai créé une première migration qui génère la table prediction_logs avec un identifiant UUID, la date, le payload de requête et les sorties du modèle. L’intérêt, c’est que le schéma est maintenant versionné et reproductible, au lieu de dépendre d’une création manuelle. J’ai également préparé la configuration locale pour éviter un projet qui ne tourne que sur mon poste dans des conditions particulières. J’ai mis à jour .env.example pour expliciter les variables nécessaires et ajouté un compose.yaml pour lancer PostgreSQL facilement en local. Sur la qualité, j’ai renforcé les tests et la CI. Les tests ne couvrent plus seulement l’API de base, mais aussi les états de santé, les erreurs de validation et la persistance en base. Aujourd’hui, dans l’état courant sans base active, la suite donne 8 tests passés et 3 ignorés, ce qui est normal puisque les tests d’intégration DB attendent une base. J’ai aussi rejoué la validation complète avec PostgreSQL actif et migration appliquée, et dans ce cas j’obtiens 11 tests passés. C’est important pour moi parce que ça prouve que la partie base n’est pas seulement codée : elle fonctionne réellement. En parallèle, j’ai mis à jour la CI GitHub Actions pour qu’elle démarre un service PostgreSQL, restaure le modèle chiffré, applique les migrations et exécute les tests et le lint. Donc on est passé d’un projet simplement lançable à un projet déjà plus industrialisé. Si je résume honnêtement où j’en suis, j’ai maintenant un socle technique solide : API, validation, traçabilité optionnelle, migration, tests et CI. Ce qu’il me reste à faire, c’est surtout stabiliser et versionner proprement ce sprint, préparer une démonstration fluide du parcours complet, et continuer l’alignement avec les attentes de la soutenance. J’ai aussi le point administratif de la soutenance du projet 4 à sécuriser si ce n’est pas déjà fait. Donc aujourd’hui, je considère que le projet a dépassé le stade du démarrage. J’ai une base sérieuse, démontrable, et je peux maintenant avancer sur la consolidation plutôt que sur la simple mise en place.
