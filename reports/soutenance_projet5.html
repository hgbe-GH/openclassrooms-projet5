Slide 4

API FastAPI et architecture applicative

1. Client -> POST /predict ou GET /health
2. Validation Pydantic du payload et des bornes
3. Chargement du modele XGBoost et preprocessing
4. Calcul de probabilite_attrition, prediction_attrition, threshold
5. Journalisation dans PostgreSQL si la base est configuree
6. Retour JSON et supervision via /health

Endpoints livres

  • GET /health
  • POST /predict
  • GET /docs

Choix d'architecture

  • separation API / modele / DB
  • validation avant inference
  • persistance obligatoire si DB configuree

Slide 8

PostgreSQL et preuve SQL locale

Preuve approfondie

Table `prediction_logs`

  • id et created_at
  • request_payload en JSONB
  • score, decision binaire, seuil
  • model_identifier
Artefacts livres

BDD et seed

  • scripts/create_db.py
  • scripts/seed_prediction_logs.py
  • sql/create_prediction_logs.sql
  • references/prediction_logs_examples.csv
Commande a lancer

Preuve SQL locale

uv run python - <<'PY'
from sqlalchemy import create_engine, text
from openclassrooms_projet5.config import get_database_url
engine = create_engine(get_database_url(), future=True)
with engine.connect() as connection:
    result = connection.execute(
        text("SELECT prediction_attrition, model_identifier, "
             "request_payload->>'poste' AS poste "
             "FROM prediction_logs ORDER BY created_at DESC LIMIT 1")
    )
    print(dict(result.mappings().one()))
engine.dispose()
PY
Resultat attendu

1 ligne recente avec :

  • prediction_attrition
  • model_identifier
  • poste

Cette partie reste locale car le Space public ne journalise pas dans PostgreSQL.

Choix technique important

Le `JSONB` permet de conserver le payload complet pour l'audit sans rigidifier inutilement le schema de logging.
