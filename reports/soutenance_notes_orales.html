Ouverture

Bonjour. Je vais vous presenter mon Projet 5 OpenClassrooms. Mon objectif etait de transformer un modele de prediction d'attrition en service exploitable, avec une API FastAPI documentee, securisee, testee et reliee a PostgreSQL. Je vais d'abord presenter les livrables, puis faire une demonstration courte, et enfin expliquer mes choix techniques.

Script slide par slide

Slide 1 - Contexte et objectif

Le besoin de Futurisys etait de rendre un modele ML utilisable via une API. Mon role a donc ete de passer d'un modele isole a un service d'ingenierie, deployable et demonstrable.

Slide 2 - Depot Git

J'ai structure le depot pour separer l'API, la logique modele, la base, les scripts, les tests et la documentation. Cette organisation facilite la maintenance, la preuve technique et le deploiement.

Slide 3 - CI/CD

Le pipeline GitHub Actions installe l'environnement, demarre PostgreSQL, restaure le modele, applique les migrations, lance les tests et le lint, puis prepare le deploiement Hugging Face sur tag. La qualite est donc verifiee automatiquement.

Slide 4 - API et architecture

Le flux est simple : le client envoie un payload, Pydantic valide, le modele calcule la prediction, puis l'API journalise en base si PostgreSQL est configure. J'ai volontairement separe API, modele et persistance pour garder une architecture claire.

Slide 5 - Swagger et securite

J'utilise Swagger pour montrer le contrat de l'API, les schemas et les erreurs documentees. La route metier `POST /predict` est protegee par `X-API-Key`, tandis que `/health` reste public pour la supervision.

Slide 6 - Demonstration

Je m'appuie sur un tableau de bord local qui orchestre la demonstration publique du Space et les preuves locales. Cela m'evite de multiplier les manipulations pendant l'oral.

Slide 7 - Tests et couverture

J'ai couvert les cas nominaux et les cas d'erreur critiques : chargement du modele, auth, validation, persistance, configuration et integration PostgreSQL. Aujourd'hui, le projet passe 69 tests avec 96% de couverture.

Slide 8 - PostgreSQL

PostgreSQL sert a la tracabilite. La table `prediction_logs` conserve le payload en `JSONB`, le score, la decision, le seuil et l'identifiant du modele. Cela permet l'audit et prepare une exploitation analytique.

Slide 9 - Usages metier

La solution permet d'auditer une prediction, de suivre le volume des appels, d'observer la distribution des scores et de comparer plusieurs versions de modele.

Slide 10 - Conclusion

En conclusion, j'ai transforme un modele ML en service exploitable, avec une API documentee, une securisation simple, une base de trace, des tests automatises et un deploiement public sur Hugging Face Spaces.

Demo en 2 minutes

Ce que je fais

  1. J'ouvre le tableau de bord local avec `./scripts/start_demo.sh`.
  2. Je montre Swagger sur le Space public.
  3. Je montre `401` sans cle.
  4. Je montre `200` avec la cle de demo.
  5. Je montre la trace PostgreSQL locale.
  6. Je montre la carte qualite.

Ce que je dis

Je commence par la preuve publique. Ici, Swagger montre le contrat de l'API. Sans cle, `POST /predict` retourne `401`, ce qui prouve que l'authentification est active. Avec la cle de demo, l'API retourne `200` avec la probabilite, la decision et le seuil. Je montre ensuite la preuve locale en base, puis la qualite logicielle.

Questions probables

Pourquoi FastAPI ?

J'ai choisi FastAPI parce qu'il combine exposition HTTP, validation Pydantic et documentation Swagger/OpenAPI nativement.

Pourquoi PostgreSQL ?

Parce que je voulais une vraie trace des predictions, exploitable pour l'audit et pour de futurs usages analytiques.

Pourquoi `JSONB` ?

Pour conserver le payload complet sans rigidifier inutilement le schema, tout en gardant la possibilite de requeter certains champs.

Pourquoi `/predict` retourne `503` si la base est indisponible ?

Parce que si la base est configuree, la tracabilite fait partie du contrat de service. Je ne veux pas accepter une prediction metier sans log.

Pourquoi Hugging Face Spaces ?

Pour montrer que le projet n'est pas seulement local. Le Space est la version publique deployee de mon API.

Pourquoi la base n'est-elle pas au centre de la demo publique ?

Parce que le Space sert surtout a prouver le deploiement public de l'API. La persistance est mieux demontree localement, de facon plus fiable.

Comment garantissez-vous la qualite ?

Par les tests Pytest, la couverture, le lint Ruff et leur execution automatique dans la CI GitHub Actions.

Si vous aviez plus de temps ?

J'ajouterais une authentification plus robuste, un dashboard analytique et davantage d'observabilite sur le service.
